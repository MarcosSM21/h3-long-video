# h3-long-video Constitution

## Core Principles

### I. Incremental Spec-Driven Development
Every feature MUST have a specification, implementation plan, ordered tasks, and acceptance
criteria before implementation begins. Each increment MUST be small enough to verify on its own
and MUST leave the repository in a usable state. This makes the pipeline understandable and
reduces the cost of diagnosing video-processing failures.

### II. Simplicity Before Abstraction
The project MUST prefer clear Python code, few dependencies, and single-purpose responsibilities.
It MUST begin with Python and the ComfyUI API. Custom nodes, framework layers, and abstractions
MUST NOT be added until a demonstrated need cannot be met clearly with the existing approach.

### III. Temporal Integrity Is Explicit
Every chunk and assembled output MUST record its source bounds, frame count, and FPS. Any
normalization, padding, trimming, frame-rate conversion, or duration change MUST be specified and
verified. Preserving source order and intended duration is a distinct requirement from preserving
the visual fidelity of motion generated by H3.

### IV. Proportionate Verification and Reproducibility
Relevant behavior—especially chunk boundaries, ordering, duration, and execution errors—MUST be
tested. CPU-only automated tests MUST be separated from validations that require a live ComfyUI
installation and GPU. Runs MUST record their effective configuration and results. A fixed seed
MUST NOT be represented as a guarantee of identical generated video.

### V. Configurable, Preserved Integration
The original ComfyUI workflow MUST be preserved unchanged. Pipeline execution MUST use copies and
explicit parameters. H3 constraints and node behavior MUST be verified in the installed ComfyUI
environment, and every unverified assumption MUST be documented before it is relied upon.

### VI. Learning-Focused Communication
Each increment MUST briefly explain the component being added and its purpose in the pipeline. Its
completion record MUST state the new capability, the evidence used to verify it, and remaining
limitations. Explanations MUST help a contributor understand both ComfyUI concepts and workflow
construction without obscuring operational facts.

### VII. Clean Public Repository
Version control MUST include publishable code, specifications, and safe examples. It MUST exclude
secrets, personal paths, model files, private media, and local execution results. Documentation and
examples MUST be reviewed for those exclusions before they are added to the repository.

## H3 and ComfyUI Integration Constraints

- Workflow inputs, output locations, chunk limits, and H3-related parameters MUST be configurable
  rather than embedded as machine-specific values.
- The project MUST retain a trace from each output segment to its input segment and workflow copy.
- Changes to workflow JSON or node assumptions MUST identify the installed ComfyUI and relevant
  node versions when that information affects behavior.
- Failures from ComfyUI MUST retain enough context to reproduce the request without exposing
  excluded repository data.

## Increment Lifecycle and Evidence

Before implementation, contributors MUST define observable acceptance criteria for the increment.
During implementation, they MUST keep deterministic processing concerns separate from generative
quality evaluation. Before closure, they MUST record the verification performed, including whether
it was automated without GPU or executed against ComfyUI, plus known limitations and deferred work.
An increment that changes timing, chunk construction, or assembly MUST include evidence that the
output ordering and declared timing conform to its specification.

## Governance

This constitution supersedes conflicting project practices. Amendments MUST be proposed as a
documented change to this file, including a Sync Impact Report, rationale, and any required
migration or follow-up work. The Sync Impact Report MUST remain as an HTML comment and MUST be
updated with each constitution amendment. Approval of an amendment occurs through the project's
normal review process.

Constitution versions use semantic versioning: MAJOR for incompatible changes that remove or
redefine principles or governance rules, MINOR for new obligations, and PATCH for clarifications
that do not change meaning. Every specification, plan, task list, review, and implementation
closure MUST check applicable compliance with these principles; exceptions MUST be explicit,
time-bounded, and documented with rationale.
